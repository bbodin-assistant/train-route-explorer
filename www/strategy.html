Layout Boundary No cloud

Implementation note / Old-web deployment, modern local compute

No backend process. No cloud runtime. Just files, browser APIs, and Rust compiled to Wasm.

The app is built like an old static website: HTML for structure, CSS for layout, JavaScript for browser coordination, and a compiled binary served next to the page. The difference is that the binary is WebAssembly produced from Rust, so the browser can run the heavy backend logic locally.

01 / Project

Treat the server like 1998

The runtime server should only answer GET requests for files.

The browser downloads HTML, CSS, JavaScript, the generated Wasm loader, and the .wasm binary. There is no application server at runtime. That constraint is useful because it forces all runtime dependencies to be explicit browser APIs: DOM, module workers, fetch, WebAssembly, and optional persistent storage.

For a different app, keep the same split. Put interface files under www/. Put Rust under src/. Compile Rust with wasm-pack into pkg/. Copy www/ and pkg/ into dist/. Publish only dist/. GitHub Pages is used as a static file shelf, not as a backend.

Build target used by this project

build:
	wasm-pack build --target web --out-dir pkg
	rm -rf "$(DIST_DIR)"
	mkdir -p "$(DIST_DIR)"
	cp -a www/. "$(DIST_DIR)/"
	cp -a pkg "$(DIST_DIR)/pkg"
02 / Runtime

Local process model

Split the app by runtime, not by framework.

The UI thread should never run the expensive algorithm. The worker should not contain domain rules. Rust should not know about the DOM. The interface between the worker and Rust should be coarse: pass a complete input and configuration in, return a complete result out.

01 index.html document

Static markup, form controls, containers for rendered output.

02 app.js UI state

Reads controls, sends commands, renders worker responses.

03 worker.js runtime bridge

Loads Wasm, owns long-running work, reports progress and errors.

04 lib.rs Wasm core

Parses input, validates data, runs algorithms, serializes results.

A

HTML/CSS

Use normal browser markup. A form, buttons, status text, and output containers are enough for many tools. No build step is needed for the UI.

B

JavaScript

Use JavaScript as glue: read controls, start the worker, pass messages, keep UI state, and render returned plain objects.

C

Rust/Wasm

Put the backend-shaped part here: parsing, validation, indexing, search, scoring, simulation, or any deterministic CPU work.

03 / Recipe

Repeatable build order

The implementation sequence I would reuse.

  1. 01

    Create the Rust crate as a Wasm library.

    The crate must compile as cdylib. Use wasm-bindgen for exported functions and serde-wasm-bindgen to convert typed Rust structs to and from JavaScript values. 

    [lib]
crate-type = ["cdylib"]

[dependencies]
wasm-bindgen = "0.2"
serde-wasm-bindgen = "0.6"
serde = { version = "1", features = ["derive"] }
  2. 02

    Export a small API from Rust.

    Do not expose one Wasm function per tiny operation. Crossing the JS/Wasm boundary has serialization cost. Export functions that map to application-level operations, such as building an index and querying that index. 

    #[wasm_bindgen]
pub fn build_context(bytes: &[u8], config_value: JsValue) -> Result<JsValue, JsValue> {
    let config: BuildConfig = from_js(config_value)?;
    let context = build_domain_context(bytes, config)?;
    to_js(&context)
}

#[wasm_bindgen]
pub fn query_context(context_value: JsValue, request_value: JsValue) -> Result<JsValue, JsValue> {
    let context: AppContext = from_js(context_value)?;
    let request: QueryRequest = from_js(request_value)?;
    to_js(&run_query(&context, &request))
}
  3. 03

    Use typed request and response structs.

    Treat the Wasm boundary as an API contract. JavaScript sends plain objects. Rust immediately deserializes them into typed structs, validates them, and returns typed output. This keeps algorithm code independent from browser object shapes. 

    #[derive(Debug, Clone, Serialize, Deserialize)]
struct BuildConfig {
    selected_inputs: Vec<String>,
    max_depth: usize,
}

#[derive(Debug, Clone, Serialize, Deserialize)]
struct QueryRequest {
    selected_day: Option<String>,
    limit: usize,
}
  4. 04

    Load the generated Wasm module inside a module worker.

    The generated pkg/*.js file is an ES module when built with --target web. Import it from a worker, call init() once, then call exported Rust functions from worker command handlers. 

    import init, { build_context, routes_for_day } from "./pkg/train_route_explorer.js";

let wasmReady = false;
let activeContext = null;

async function ensureWasm() {
  if (!wasmReady) {
    await init();
    wasmReady = true;
  }
}

self.onmessage = async (event) => {
  await ensureWasm();
  if (event.data.type === "build") {
    activeContext = build_context(event.data.bytes, event.data.config);
    self.postMessage({ type: "ready", context: activeContext });
  }
};
  5. 05

    Transfer binary input instead of copying it.

    If the app reads a file, send the ArrayBuffer to the worker as a transferable. The main thread loses ownership of that buffer, and the browser avoids an unnecessary memory copy. 

    const worker = new Worker("./worker.js", { type: "module" });
const buffer = await file.arrayBuffer();

worker.postMessage(
  { type: "load-upload", buffer, name: file.name, config },
  [buffer],
);
  6. 06

    Keep UI state in JavaScript, not in the DOM.

    The DOM is a rendering target. Store selected options, current result, dirty flags, progress, and error state in a JavaScript object. Re-render from that state when the worker sends progress, ready, result, or error. 

    worker.onmessage = (event) => {
  if (event.data.type === "progress") updateProgress(event.data);
  if (event.data.type === "ready") renderReadyState(event.data.context);
  if (event.data.type === "result") renderResult(event.data.result);
  if (event.data.type === "error") renderError(event.data.message);
};
  7. 07

    Do not confuse memory, HTTP cache, and IndexedDB.

    Worker variables survive while the page is open. They do not survive a reload. In this app, the GTFS bytes live in worker memory as archiveBytes, so opening the same page again starts from null. IndexedDB is used for expensive derived output, not for the original zip file. 

    let archiveBytes = null;
let sourceMeta = null;
let activeContext = null;

async function fetchArchive(url) {
  const response = await fetch(url, { cache: "no-store" });
  const buffer = await response.arrayBuffer();
  return { bytes: new Uint8Array(buffer), meta: { url } };
}

    That means a cached context can avoid rebuilding the Rust/Wasm index, but the app still needs source bytes after a reload to identify or rebuild that context. With cache: "no-store", even the browser HTTP cache is bypassed for the bundled archive.

    If the requirement is "open the app tomorrow and do not download or choose the source file again", store the source bytes in IndexedDB as a separate object store. Key it by a content hash or stable release version, then load it before falling back to network or file upload. 

    const key = JSON.stringify({
  version: "app-context-v1",
  sourceHash,
  buildConfig,
});

const tx = db.transaction(["sources", "contexts"], "readwrite");
tx.objectStore("sources").put({ bytes: archiveBytes, meta: sourceMeta }, sourceHash);
tx.objectStore("contexts").put(activeContext, key);
  8. 08

    Publish the static build to GitHub Pages.

    The action installs the Rust Wasm target, installs wasm-pack, runs the static build, uploads dist/, and deploys that artifact to Pages. GitHub Pages then serves the files. It does not run the app logic. The browser runs the app logic after downloading those files. 

    - name: Install Rust WASM target
  run: rustup target add wasm32-unknown-unknown

- name: Install wasm-pack
  run: cargo install wasm-pack --locked --version 0.15.0

- name: Build static site
  run: make build

- name: Upload GitHub Pages artifact
  uses: actions/upload-pages-artifact@v3
  with:
    path: dist

- name: Deploy to GitHub Pages
  uses: actions/deploy-pages@v4
04 / Checks

Where this stops working

This pattern is old-web hosting with local compute, not magic.

Use it when

  • The app can run with browser APIs only.
  • The heavy logic is deterministic and local to one user.
  • The input and derived state fit target browser memory.
  • The Rust API can be expressed as a few coarse functions.
  • A static directory is a valid release artifact.

Do not use it when

  • The app needs secrets, private tokens, or privileged network calls.
  • Users must share authoritative mutable state.
  • The dataset is too large for browser memory.
  • The computation must run on a schedule without a browser open.
  • You need server-side indexing across many users.
05 / Template

Copyable skeleton

The whole deployment can stay this boring.

Local build

rustup target add wasm32-unknown-unknown
cargo install wasm-pack --locked
wasm-pack build --target web --out-dir pkg
mkdir -p dist
cp -a www/. dist/
cp -a pkg dist/pkg

Local test server

python3 -m http.server 8080 --directory dist

Test the built directory over HTTP, not by opening the file directly. Module workers and Wasm imports are URL-based, so the deployed behavior is closer to python3 -m http.server --directory dist than to file://. After that, the only production step is serving the same directory from GitHub Pages.
